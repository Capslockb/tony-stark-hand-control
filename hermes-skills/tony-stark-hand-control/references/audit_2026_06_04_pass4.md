# Audit Pass 4 — Historical Notes

This dated note records observations about single-instance handling, camera startup, and Windows resource failures from one development revision. It is not a current validation report or a process-recovery runbook.

## Single-instance handling

The application uses process-owned locking mechanisms to reduce duplicate launches. A correct implementation should acquire the lock before constructing expensive runtime objects where practical, release owned handles on every normal exit path, and surface an existing application window without terminating unrelated processes.

A leftover lock file is not evidence of a live owner. Deleting a file cannot release a named mutex or advisory lock held by another process. Recovery guidance should first identify the executable, process owner, desktop session, start time, visible window, and camera ownership.

## Camera startup

Some camera backends need warm-up reads before exposure and frame delivery stabilize. Probing logic should:

- bound the number and duration of open/read attempts;
- release every rejected capture object;
- distinguish a failed read from a dark but valid scene;
- avoid blocking the graphical event thread;
- support cancellation and cleanup when startup is abandoned;
- use deterministic mocked tests for slow, blocked, and unsuccessful opens.

Backend behavior is device- and driver-specific. A fixed warm-up count is not a universal guarantee.

## Windows resource failures

`WinError 1455` can indicate that the system commit limit cannot satisfy a new allocation. Free physical memory alone does not determine available commit capacity. Troubleshooting should inspect current commit usage, paging-file configuration, and verified process ownership before closing applications or changing system settings.

Do not publish machine-specific process names, memory figures, force-termination commands, or a single host observation as a universal remedy. Attempt graceful shutdown first and avoid terminating processes that have not been positively identified.

## Validation boundary

Current source, repository tests, exact-head CI, and controlled Windows testing take precedence over this note. Syntax checks and short-lived process observations do not establish camera readiness, lock correctness, or stable runtime behavior.
