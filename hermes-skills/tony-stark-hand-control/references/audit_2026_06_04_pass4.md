# Audit pass 2026-06-04 (fourth pass) — single-instance lock + MSMF warm-up + pagefile exhaustion

This pass added the "single-instance" guarantee and uncovered a
class of failure that didn't appear in earlier audits: **pagefile
exhaustion from orphan helper processes silently sabotages every
fresh `cv2` import on this host**.

## 18. Single-instance lock: named mutex + file lock, with window surfacing

A Tkinter app that the user can launch from a desktop shortcut is
**guaranteed to be double-clicked again** if the first launch is
hidden behind another window. Each copy grabs the same cameras,
the OS hands out separate OpenCV windows, and the user has two
uncoordinated instances fighting for the webcam. The fix is a
single-instance lock that runs *before* any expensive imports.

The recipe is **two layers of locking, because each can fail in
its own way**:

```python
import tempfile, ctypes
from ctypes import wintypes

class _SingleInstance:
    def acquire(self):
        # Layer 1: Windows named mutex (kernel object).
        # Cross-session, robust to crashed prior owners.
        kernel32 = ctypes.WinDLL('kernel32', use_last_error=True)
        CreateMutexW = kernel32.CreateMutexW
        CreateMutexW.restype = wintypes.HANDLE
        h = CreateMutexW(None, False, 'Global\\TonyStarkHandControl_v1')
        if h and ctypes.get_last_error() == 183:  # ERROR_ALREADY_EXISTS
            kernel32.CloseHandle(h)
            self._surface_existing_window()
            return False
        self._mutex = h

        # Layer 2: file lock via msvcrt.locking (fallback).
        # The mutex is enough on Windows but the file lock survives
        # if the app is launched via a non-Windows wrapper (WSL, etc).
        self._fd = open(os.path.join(tempfile.gettempdir(),
                                     'tony_stark.lock'), 'w')
        try:
            import msvcrt
            msvcrt.locking(self._fd.fileno(), 2, 1)  # LK_NBLCK, 1 byte
        except OSError:
            # Held by another process.
            self._fd.close(); self._fd = None
            return False
        return True
```

**Key design choices:**

1. **Acquire the lock *before* `import tkinter` or `import cv2`.**
   The lock failure path is the common case (user double-clicked),
   so it should be cheap. A 5-second cv2 import just to print
   "already running" is awful UX.

2. **Surface the existing window, don't just show a message box.**
   EnumWindows → match on `'Tony Stark' in title` → `SetForegroundWindow`.
   The user gets the right behavior automatically: their app comes
   to the front. Fall back to a `messagebox.showinfo` only if no
   matching window is found.

3. **Set `WM_DELETE_WINDOW` to release the lock.** If you only
   release on process exit, the lock leaks until the OS reaps the
   mutex (which can be days if the user closes via Task Manager's
   "End Task" without the process actually dying immediately).

4. **Wrap release in `finally:`** in the entry point. The lock must
   be released on every exit path including Ctrl-C in the terminal.

**On non-Windows / WSL:** wrap both layers in `try/except` and
don't fail the launch if `msvcrt` is missing. The mutex is
Windows-only; the file lock is too. The app should still launch
on Linux even though "single instance" can't be enforced — just
log a warning.

## 19. MSMF camera warm-up: read 5 frames, not 1, in `_find_cameras`

`cv2.VideoCapture(idx, cv2.CAP_MSMF).read()` returns `True` for
the first frame even on cameras that haven't finished their
sensor warm-up / auto-exposure pipeline. The first frame is
**often entirely black** for 1-5 reads. If you accept a camera
on the basis of that first read, it gets added to the manager,
then the live-feed check on every subsequent read says "black",
and the cam is blacklisted for the whole session.

```python
def _find_cameras(self, w, h, fps):
    for idx in range(6):
        for backend in [cv2.CAP_DSHOW, cv2.CAP_MSMF, cv2.CAP_ANY]:
            cap = cv2.VideoCapture(idx, backend)
            if not cap.isOpened():
                cap.release(); continue
            cap.set(cv2.CAP_PROP_FPS, fps)
            cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)
            cap.set(3, w); cap.set(4, h)
            # Read 5 frames to flush MSMF warm-up / auto-exposure.
            last_good = False
            for _ in range(5):
                ret, frame = cap.read()
                if not ret or frame is None:
                    continue
                if self.is_feed_live(True, frame):
                    last_good = True
            if last_good:
                self.cameras.append(cap)
                print(f"  Auto-detected camera {idx} (backend={backend})")
                break
            cap.release()
```

**Symptom of the bug:** "all my cameras show as black" when the
user just launched the app, even though a probe (e.g. the Windows
Camera app) shows them working fine. The "CameraManager opens
>=1 camera" test passes (cams were *detected*) but the live-feed
check immediately blacklists them.

**Fix:** read 5 frames and use `is_feed_live()` on the **last**
one, not the first. This is the same `is_feed_live` check used
in the main loop, so the warm-up matches the runtime check.

## 20. Pagefile exhaustion from orphan helper processes

A real production failure mode on this 32 GB Windows host: the
llama.cpp `llama-server.exe` was started three separate times
during earlier experiments and never killed. Each instance ate
~1.8 GB of RAM, and each was paging **1.4 GB out to the pagefile**.
The system had 11.5 GB of physical RAM free but the pagefile was
hot, so any new process that needed a few hundred MB for a fresh
`import cv2` hit `WinError 1455: The paging file is too small
for this operation to complete.`

The app's **previous** process was still running with cv2 already
loaded, so it kept working — but the new diagnostic probe I ran
in another terminal failed every time, and any code path that
re-imported cv2 (e.g. `python -c "import cv2; ..."`) crashed.

**Fix:** identify and kill the orphan processes:

```powershell
Get-Process llama-server -ErrorAction SilentlyContinue |
    ForEach-Object { Stop-Process -Id $_.Id -Force }
# Or check which processes are paging heavily:
Get-Process | Sort-Object -Property PagedMemorySize -Descending |
    Select-Object -First 10 Name, Id,
        @{N='PageFile_MB';E={[math]::Round($_.PagedMemorySize/1MB,1)}}
```

**The lesson:** when a fresh `import` fails with WinError 1455
or the user reports "the app started working yesterday but now
won't even import", check the pagefile, not just free RAM. The
free RAM can be huge but the pagefile still saturated if long-
running processes are paging. **This is a class of failure that
doesn't show up in standard "is the disk full" / "is RAM free"
diagnoses** — it needs `PagedMemorySize` on each process.

**The 4 orphans I killed freed 3.6 GB of RAM and the pagefile
went from "hot" to "15 GB free"** — the same `import cv2` that
failed immediately before worked 2 seconds later.

## 21. Web research: backend choice matters more than query

`web_search` and `web_extract` failed throughout this audit:

- `web_search` -> SearXNG returned HTTP 404 (the search backend
  is configured but the public SearXNG instance it points at is
  down)
- `web_extract` -> "SearXNG is a search-only backend and cannot
  extract URL content. Set web.extract_backend to firecrawl, tavily,
  exa, or parallel."

The user has not configured `firecrawl`/`tavily`/`exa` (no API
keys set), so `web_extract` is permanently broken in this
profile. **Don't waste a turn retrying — pivot to internal
audit and live runtime testing.** A 60-assertion headless test
suite catches more real bugs in 10 seconds than a flaky web
search would catch in 10 minutes.
