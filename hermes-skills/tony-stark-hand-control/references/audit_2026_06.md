# 2026-06 Code Audit — Bugs Found and Fixed

A line-by-line audit of `tony_stark_hud_control.py` (2001 lines at the
end) caught eleven real bugs. This note is the canonical record of
what broke and how it was fixed, so a future session doesn't re-introduce
the same issues when editing the file.

## Bug catalog (with severity)

| # | Severity | Location | Bug | Fix |
|---|---|---|---|---|
| 1 | 🟠 High | `HandProcessor.smooth()` | Velocity computed from `filt − predicted`, but `predicted` was set from the *previous* `out` (buffer average), not the previous single-sample filtered point. Velocity was systematically **underestimated** by ~50% (measured 0.23 vs expected 0.30). | Snapshot `prev_filtered = self.filtered[tip_id]` **before** overwriting, then compute `vx = (filt - prev_filtered) / wall_dt`. |
| 2 | 🟠 High | `HandProcessor.smooth()` | `predicted` anchor set to `out` (buffer mean) instead of `filt` (latest single sample). The predictor's velocity extrapolation anchored on a stale point, defeating the 1:1 motion-prediction feature. | Set `self.predicted[tip_id] = (filt[0], filt[1], ts)` (the most recent filtered value), not the buffer average. |
| 3 | 🟠 High | `HandProcessor.predict()` | Returned `(0.0, 0.0)` for tips that had never been detected (e.g. on the very first frame, or after a black-feed filter blackout). **Result**: gesture code interpreted `(0, 0)` as a valid fingertip in the top-left corner of the image, causing phantom "click at origin" events. | Return `None` for unseen tips. Caller (`handle_gestures`) falls back to the raw landmark for that tip. |
| 4 | 🟠 High | `HandProcessor.is_palm_open()` (static) | Used `tip.y < pip.y` to detect extended fingers. **Broken on selfie cameras** (Windows webcam default) where the Y axis is flipped — an open palm returned `False`. Engage gesture was unreliable on the most common camera config. | Use **wrist-relative distances**: a finger is extended iff `wrist_to_tip > wrist_to_pip * 1.15` AND `wrist_to_pip > wrist_to_mcp * 0.95`. Mirror-invariant. Verified against the original buggy code with `palm_bug_demo.py`. |
| 5 | 🟡 Medium | `handle_gestures` | Click distance was computed in **pixels** but applied across cameras of different resolutions. Threshold of 40px meant different things on the 480x360 hand-cam vs the 1280x720 wide-cam. | Switch to **normalized coords** (`hypot(a.x-b.x, a.y-b.y)`), auto-scale the threshold: `th = click_threshold_px / screen_height * 4`. |
| 6 | 🟡 Medium | `OllamaGestureRecognizer` | No circuit breaker. If the cloud endpoint was unreachable, the worker thread would block on the 8s timeout every 0.5s, queue would fill, and the app would appear to hang in the GUI tab. | Add `_consecutive_failures` counter; on 3 failures, trip a 30s cooldown where `submit_frame()` and the worker both no-op. Reset on next success. |
| 7 | 🟡 Medium | `CameraManager` + `start_calibration` | Calibration opens cameras but never releases them. The user's subsequent click on **Start** then either fails to open (handle conflict) or opens a *second* set that fights the first for the same device. | Add `CameraManager.release()`. In `start()`: release the previous manager first. In `start_calibration`: track whether the cameras are owned by the calibration, and release them after. |
| 8 | 🟡 Medium | `is_feed_live` defaults | `min_std=2.0, min_brightness=3.0` was too strict — out of 4 cameras, 3 had `std in [0.8, 2.5]` and `brightness in [0, 1.4]` (live but dim). They got auto-blacklisted. | Lower to `min_std=0.5, min_brightness=0.2`. Only true frozen/uniform frames fail. |
| 9 | 🟡 Medium | `predict()` docstring | Said the decay was "0.5 * (1 - (dt/max)²)" which is wrong — the actual formula `max(0, 1 - (dt/max)²)` is an ease-out curve that hits 0 at `dt=max`, not 0.5. | Fix the docstring to describe the actual behavior. |
| 10 | 🟢 Low | `handle_gestures` screen-EMA clamp | `max_step = 5000 * dt` is too tight when the predictor is feeding accurate positions. 15ms × 5000 = 75px clamp, but a fast hand moves the cursor 200+px in 15ms. The clamp was *throttling* the cursor. | Loosen to `10000 * dt` (150px at 15ms). With the predictor, the input is already accurate; only absurd teleports need to be clamped. |
| 11 | 🟡 Medium | `predict()` — initialization order | On the very first detection, `prev_filtered` is `None` and the velocity update is skipped (correct). But the predictor's `predicted[tip_id]` was set to `(out[0], out[1], ts)` where `out` is the buffer mean — which on the first call equals the raw `filt` (buffer has only 1 sample). So first-frame was OK, but the bug was that the anchor stayed as the buffer mean for all subsequent frames. | Use `filt` as the anchor directly. Buffer mean is still returned to consumers who want the smoother value, but the predictor uses the freshest. |

## Lessons for future audits

When auditing a system that has accumulated many patches:

1. **Look for state that depends on stale buffers.** Any time you see `predicted = compute(some_buffer)`, ask: is the consumer of `predicted` actually better off with the freshest sample rather than the smoothed mean? The predictor wants freshness; the cursor renderer wants smoothness. Don't conflate them.

2. **The "no data" default matters more than the "has data" computation.** `predict()` returning `(0, 0)` for unseen tips was invisible until a real consumer was built that assumed "no gesture at top-left is the same as no detection" — which it isn't. Always return `None` for "no data" and force the caller to branch.

3. **Coordinate convention bugs (Y-flip, mirroring) are silent.** A test that runs against a single camera with a known Y orientation will pass; a test with the Y axis mirrored will catch the bug. Always include a mirror test in any gesture/pose recognizer.

4. **Thresholds in `is_feed_live` and similar cheap "is this real?" probes are usually too tight.** A `std < 2` filter is a strong "is this a uniform color?" test, which is *not* the same as "is this a frozen frame from a real camera that has bad lighting." Lower the defaults; raise them only if you have evidence the false-positive rate is a problem.

5. **Any code that opens resource handles (cameras, files, sockets) needs a `release()` and the *caller* must call it on all exit paths.** Constructor opens, destructors are unreliable in Python, and `__del__` doesn't always run on app exit. Add an explicit `release()` and wire it into `Stop()`, `on_close()`, and every re-init path.

6. **External API calls in a worker thread need a circuit breaker.** When the network is flaky, the worker will block for `timeout` seconds on every request. A `N consecutive failures → 30s cooldown` pattern saves the app from looking frozen.

7. **The `_vel_history` rolling average is a noise killer, not a memory hog.** `deque(maxlen=3)` for the velocity is a sweet spot — 3 samples is enough to average out single-frame MP jitter, but few enough to respond to direction changes within ~30ms.
