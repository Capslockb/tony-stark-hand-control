# Audit pass 7 — 2026-06-04

This dated audit note records product-level observations from one development revision. It is historical context, not evidence of current behavior.

## Areas reviewed

### Application resource readout

The reviewed revision added an application-local CPU, memory, and thread-count display using Windows process APIs through `ctypes`. The intent was to distinguish the application's own resource use from system-wide load.

Important limitations:

- the first CPU sample is a baseline and should not be treated as a measurement;
- process CPU percentages require a documented normalization convention;
- working-set memory is not the same as committed or paged memory;
- the display should degrade safely when Windows APIs are unavailable;
- update work belongs on a bounded schedule rather than every rendering operation.

### Main-loop startup

The audit recommended scheduling the first processing iteration through the GUI event loop after startup state is visible. Slow camera, model, file, or network initialization should not block the graphical event thread.

This is a design goal only. Current behavior must be checked against the exact application source and the main-loop regression tests.

### Process diagnostics

When reported system load does not match the application's own readout, contributors should identify the owning process and session before terminating anything. Process names alone are not sufficient evidence.

A safe diagnostic sequence is:

1. identify the process ID, executable path, owner, session, start time, and visible window;
2. compare application-local CPU and memory with system-wide measurements;
3. verify whether the process owns cameras, model servers, or other resources;
4. attempt an ordinary graceful shutdown first;
5. use forced termination only after ownership and impact are established.

Environment-specific process observations should not become universal troubleshooting rules.

## Validation boundary

The original audit mixed implementation notes, host observations, and operational guidance. Present support claims require:

- current source inspection;
- deterministic tests tied to the exact revision;
- controlled Windows validation for Windows-specific APIs;
- confirmation that the resource display does not block or destabilize the GUI loop.

Any performance values, platform assumptions, process examples, or completion statements from the original audit should be considered superseded unless reproduced against the current tree.
