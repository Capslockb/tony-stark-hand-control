# Audit pass 5 — 2026-06-04

This dated note summarizes multi-camera rendering, pacing, and benchmark observations from one development revision. It is not a current performance claim.

## HUD rendering

The reviewed implementation rebuilt static overlay elements for every camera frame. A safer optimization boundary is to cache only content that is genuinely invariant for a frame size and redraw dynamic landmarks separately.

```python
key = frame.shape[:2]
base = self._hud_base_cache.get(key)
if base is None:
    base = self._build_hud_base(*key)
    self._hud_base_cache[key] = base
np.maximum(frame, base, out=frame)
```

Any cache must be invalidated when its inputs change. Visual correctness should be tested before treating a micro-benchmark improvement as a product improvement.

## GUI state access

Tk variable reads cross the Python/Tcl boundary. Reading each camera's enabled state once per loop and using plain Python values inside the inner frame-processing path can reduce repeated bridge calls.

```python
camera_enabled = {
    camera_index: bool(variable.get())
    for camera_index, variable in self.camera_vars.items()
}
```

Keep the values keyed by camera index so disabled, missing, or non-contiguous cameras cannot shift the state onto a different stream.

## Display-cache invalidation

Cached display frames should be refreshed whenever new inference output is paired with a new source frame. Reusing an old display beneath new landmarks can create visible mismatch.

## Camera-to-FPS mapping

FPS samples must remain associated with the camera that produced them. Mapping a compact list of live-camera measurements directly onto indices `0..N` is incorrect when cameras are disabled, missing, or blacklisted.

Prefer explicit records such as `(camera_index, fps)` or a dictionary keyed by camera index.

## Single-instance validation

Single-instance behavior should be validated with two controlled processes and clear ownership checks. A leftover file is not proof of a live lock, and deleting a file cannot release a process-owned mutex or advisory lock.

Validation should confirm that:

- the first process remains active;
- the second process exits through the intended duplicate-instance path;
- camera and lock resources are released on normal shutdown;
- recovery guidance does not terminate an unrelated process.

## Benchmark methodology

Benchmark setup work should be outside the timed section. Input generation, warm-up, copying, logging, and GUI updates can otherwise dominate the operation being measured.

```python
frames = [make_frame() for _ in range(sample_count)]
for frame in frames[:warmup_count]:
    draw_hud(frame.copy(), landmarks)

samples = []
for frame in frames:
    start = time.perf_counter()
    draw_hud(frame, landmarks)
    samples.append(time.perf_counter() - start)
```

Report the environment, frame size, camera count, sample count, median, tail latency, and projected call rate. Historical measurements from a different machine or revision are not current acceptance evidence.

## Process recovery

Before terminating a process, identify its executable, owner, session, start time, and resource ownership. Attempt graceful shutdown first. Forced termination and lock-file cleanup should not be presented as routine first-line recovery.

## Validation boundary

The current source, deterministic tests, and exact-head CI results take precedence over this note. Hardware-specific performance and multi-camera behavior require reproduction on the stated environment.
