# Audit pass 2026-06-04 (fifth pass) — multi-stream efficiency + FPS cache bug + benchmark methodology

This pass made the app actually usable with 4 cameras simultaneously
without burning an entire CPU core, fixed two new bugs found by
re-running the audit, and confirmed the "second launch is a no-op"
guarantee end-to-end.

## 22. Multi-stream efficiency: the HUD was eating 70% of one core

With 4 cameras x 30 fps the original `draw_hud` was the dominant
per-frame cost. The old implementation redrew every primitive on
every frame for every camera: a 3-rings atom with animated
rotation, 5 fingertips (3 primitives + putText + a random "fire"
particle) per cam, and a palm-center circle.

**The optimization pattern: cache the static base, only redraw
the animated part.**

```python
def draw_hud(self, frame, landmarks):
    h, w = frame.shape[:2]
    key = (h, w)
    # Build the static base ONCE per unique frame size.
    if key not in self._hud_base_cache:
        self._hud_base_cache[key] = self._build_hud_base(h, w)
    # np.maximum is a single SIMD op, not 3 cv2.circle calls.
    np.maximum(frame, self._hud_base_cache[key], out=frame)
    # Only the animated fingertip markers are redrawn each frame.
    if landmarks is not None:
        now = cv2.getTickCount()
        for tip in [4, 8, 12, 16, 20]:
            lx = int(landmarks[tip].x * w)
            ly = int(landmarks[tip].y * h)
            z = landmarks[tip].z
            cv2.circle(frame, (lx, ly), int(20 + z * 10), color, 2)
            cv2.circle(frame, (lx, ly), r, ring_color, -1)  # pulsing
            cv2.ellipse(...)  # animated arc
            cv2.putText(...)
```

**Measured cost at 480x360 (Python 3.14, RTX 5060, XNNPACK MediaPipe):**
- OLD: 5-10ms per call x 120 calls/sec (4 cams x 30 fps)
  = 600-1200ms/sec = **60-120% of one core**
- NEW: 0.2ms per call = 24ms/sec = **2.4% of one core** (25-50x speedup)

Breakdown of the new cost:
- `np.maximum` for the cached base: 0.013ms (single SIMD op on 480x360x3)
- 5 fingertip markers (3 cv2.circle + 1 cv2.ellipse + 1 cv2.putText per tip): 0.19ms

## 23. Per-cam enable state: cache the Tk var reads

`self.camera_vars[i].get()` looks like a cheap dict lookup but
each call goes through Tk's Tcl bridge. With 4 cams x 30 fps
that's 120 Tcl round-trips per second on the hot path.

**Fix:** cache as a plain Python list once per loop iteration:

```python
cam_enabled = [bool(self.camera_vars[i].get())
               if i < len(self.camera_vars) else False
               for i in range(len(raw))]
# ...then use cam_enabled[i] inside the inner loop
```

This drops the per-frame Tcl bridge cost to 4 calls per loop
(one per cam) regardless of how many cameras you have.

## 24. The `if run_mp: self._last_displays = {}` pattern

Display caching across MediaPipe frames is a real win (skips
`frame.copy()` on intermediate frames = 0.5ms per cam per frame
saved), BUT the cache must be invalidated on the MediaPipe frame
or you'll show the previous MediaPipe frame's display with the
new frame's landmarks on top — a subtle but visible stutter.

The right pattern is:

```python
if run_mp:
    self._last_displays = {}  # force fresh copies this iter
for i, (ret, frame) in enumerate(raw):
    ...
    display = self._last_displays.get(i)
    if display is None or run_mp:
        display = frame.copy()
    self._last_displays[i] = display
```

Don't try to be cleverer and check if landmarks changed — the
landmarks ARE the data, and the frame underneath them is the
visual context. If MediaPipe ran, both need to be redrawn.

## 25. Off-by-one in the FPS cache (silent data corruption)

The original code:

```python
if check_fps and live_fps:
    for i, f in zip(range(len(live_fps)), live_fps):
        self._fps_cache[i] = f
```

This is **wrong** when the camera order is not 0, 1, 2, 3 — e.g.
if cam 0 is disabled or blacklisted, `live_fps` starts at the
index of the *first live cam*, not at 0. The fix walks both
lists in lockstep with a separate cursor:

```python
if check_fps and live_fps:
    cam_sample_idx = 0
    for i in range(len(raw)):
        if i in self._live_cache and self._live_cache[i]:
            if cam_sample_idx < len(live_fps):
                self._fps_cache[i] = live_fps[cam_sample_idx]
                cam_sample_idx += 1
```

**Symptom of the bug:** pacing in the main loop would target the
wrong FPS (a cam at 60 fps would pace as if it were 30 fps, or
vice versa), causing either loop saturation or a sluggish loop.
Often invisible if all cams run at the same FPS, but breaks
immediately when you have one fast cam and one slow cam.

## 26. Single-instance lock: end-to-end test, not just unit test

The `_SingleInstance` class has unit tests for acquire/release
(3/3 pass in `single_instance_test.py`), but the **real** test
is: launch one instance, launch a second, watch the second one
exit within 2 seconds with code 0.

Recipe for verifying the lock works end-to-end from this host:

```bash
# 1. Start instance 1 in background
hermes process run "python tony_stark_hud_control.py" --background
# 2. Start instance 2 in background (after a brief settle)
sleep 1
hermes process run "python tony_stark_hud_control.py" --background
# 3. Poll instance 2
hermes process poll <session_id_2> --timeout 8
# Expected: status="exited", exit_code=0
# 4. Verify instance 1 is still running
hermes process poll <instance_1_session_id>
# Expected: status="running"
# 5. Verify only ONE Tony Stark python process exists
powershell -NoProfile -Command "Get-Process python |
    Where-Object { $_.MainWindowTitle -like '*Tony Stark*' } |
    Measure-Object | Select-Object -ExpandProperty Count"
# Expected: 1
```

**Anti-pattern: cleaning up orphan lock files manually between
tests.** If you find yourself `rm -f $TEMP/tony_stark.lock`
between test runs, you have a bug: the lock should be released
by the process on clean exit. The `try/finally` in the entry
point and the `WM_DELETE_WINDOW` handler cover this; if either
fires incorrectly, fix the underlying code, don't work around
it by deleting the lock file.

## 27. Benchmarking real cv2 work: a 5ms gotcha in micro-benchmarks

A common mistake when benchmarking cv2 code: include
`frame = (np.random.rand(360, 480, 3) * 255).astype(np.uint8)`
in the timed loop. That single line is **~5ms on its own** (numpy
randn + multiply + astype), which drowns out the cv2 work you're
trying to measure and makes the optimization look useless.

Recipe for valid cv2 micro-benchmarks:

```python
# Pre-generate frames OUTSIDE the timed loop
frames = [(np.random.rand(360, 480, 3) * 255).astype(np.uint8)
          for _ in range(N)]

# Warmup (JIT, cache, etc.)
for f in frames[:3]:
    draw_hud(f.copy(), lm)

# Real measurement
import time
times = []
for f in frames:
    t0 = time.perf_counter()
    draw_hud(f, lm)
    times.append((time.perf_counter() - t0) * 1000)

print(f'median: {np.median(times):.3f}ms')
print(f'p95:    {np.percentile(times, 95):.3f}ms')
print(f'at 120 frames/sec: {np.median(times)*120:.0f}ms/sec '
      f'= {np.median(times)*120/10:.1f}% of one core')
```

**Always report BOTH the per-call cost AND the projected CPU
utilization at the target frame rate.** A 5ms call sounds fast
in isolation but is 600ms/sec = 60% of a core at 120 fps.

## 28. `random.randint` is not free on the hot path

Lesson from removing the "fire" particles: any `random.randint`
call inside a per-frame loop is ~0.5-1 microsecond. That sounds
cheap but at 4 cams x 5 tips x 4 randoms x 30 fps = 2400
calls/sec = 1.2-2.4ms/sec. Not catastrophic on its own, but
pure waste.

**Audit your draw functions for `random.*` calls.** Most are
decorative particles (sparks, fire, snow) and can be:
- Removed entirely (no one misses them in 30 fps)
- Pre-computed once per N frames
- Replaced with a deterministic function of the wall clock

## 29. The "second app won't start" pattern: kill, not relaunch

When the user reports "the app doesn't start", the most common
cause on this host is **a previous instance is still holding
the single-instance lock OR a previous instance is still holding
the camera handles**. The diagnostic sequence:

1. `hermes process list` -> find any Tony Stark processes
2. `powershell -NoProfile -Command "Get-Process python |
   Where-Object { $_.MainWindowTitle -like '*Tony Stark*' } |
   Select-Object Id, StartTime, MainWindowTitle | Format-Table"`
3. If multiple, kill all but the most recent:
   `Stop-Process -Id <id> -Force`
4. `ls -la "$TEMP/tony_stark_hud.lock"` -> if present and no
   python is running, `rm -f` it (orphaned lock)
5. `Get-Process | Sort-Object PagedMemorySize -Descending |
   Select-Object -First 5 Name, Id, PagedMemorySize` -> check
   for orphan model servers eating swap
6. Retry the launch

The "kill all but most recent" rule is important: if the user
ran the app an hour ago and the old window is still hidden
behind something, the *new* launch is the one that should win.
