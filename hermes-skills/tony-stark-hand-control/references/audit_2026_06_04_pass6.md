# Audit Pass 6 (2026-06-04) — Start-button GUI freeze + camera-probe timeouts

User feedback signal: "extreme lag when pressing Start". After
audit pass 5's HUD optimization, the user reported the START button
itself was laggy. Investigation revealed two distinct bugs:

## Bug A — `start()` runs a slow synchronous CameraManager.__init__ on the Tk main thread

`start()` called `CameraManager(width=480, height=360, fps=30)`,
which in turn calls `_find_cameras`, which probes 6 indices × 3
backends × 5 reads = 90 blocking `cap.read()` calls. On Windows
with 4 cameras, this took 5-30+ seconds. Worse, `start()` then
called `self.loop()` synchronously, so the FIRST MediaPipe
inference + 4 cam reads all ran on the GUI thread BEFORE any
"Running" status was painted. The user saw a frozen window.

### Fix

Two-part fix:

1. **Move camera open to a background thread** so the GUI stays
   responsive. New `_start_worker()` runs the cv2 work; the
   results are handed back via `self.root.after(0, _start_finish_gui)`
   so Tk widget updates are on the main thread (mandatory).

2. **Schedule the first loop with `root.after(50, ...)`** instead
   of calling `self.loop()` synchronously. The 50ms delay gives
   the GUI time to paint the "Running" status, the new camera
   widgets, and the Start/Stop button state changes BEFORE the
   first loop iteration blocks on MediaPipe.

The user now sees the status change to "Starting... opening
cameras" instantly, then "Running with N camera(s)" once the
cameras are actually open.

## Bug B — `cap.isOpened()` does NOT protect against slow webcam drivers

Even with `_find_cameras` reading 5 frames per backend, the
probe could still take 30+ seconds. Investigation: `cap.isOpened()`
returns `True` for many "phantom" device indices on Windows
DSHOW/MSMF, but the first `cap.read()` blocks waiting for
hardware that isn't there.

### Fix — OpenCV timeout props

OpenCV 4.5+ exposes two videoio properties that bound the
blocking time:

- `cv2.CAP_PROP_OPEN_TIMEOUT_MSEC` (53) — caps `cap.open()` time
- `cv2.CAP_PROP_READ_TIMEOUT_MSEC` (54) — caps `cap.read()` time

Setting them on each `VideoCapture` (BEFORE any read attempts)
makes the worst-case probe time bounded. After the fix, 4
cams with DSHOW on this host:
- cam 0: open 569ms, total 3570ms
- cam 1: open 546ms, total 1721ms
- cam 2: open 2440ms, total 5441ms
- cam 3: NOT OPENED in 2ms (no device)
Total: ~10 seconds for 4 cams, with no single read blocking
beyond the 1500ms / 800ms timeouts.

Combined with the worker-thread refactor (Bug A), the GUI no
longer freezes during camera open.

## Class-level lessons (extracted to `gui-app-startup` skill)

These are reusable across any Tkinter / PyQt / wxPython GUI app
that does slow init in response to a user click — not specific
to this project. See the new umbrella skill.

## Diagnostic recipe for "GUI freezes on click"

1. Add print() / status_label.update() calls around each phase
   of the click handler to localize the blocking call.
2. If the handler does any of: `cv2.VideoCapture(...).read()`,
   `pip install`, large `np.array` allocation, file load from
   network share, GPU init — that's the culprit. Move to
   `threading.Thread(daemon=True)` + `root.after(0, ...)` for
   the GUI half.
3. If the inner call is cv2 specifically, ALSO set
   `CAP_PROP_OPEN_TIMEOUT_MSEC` and `CAP_PROP_READ_TIMEOUT_MSEC`
   on every `VideoCapture` to bound the worst case.
